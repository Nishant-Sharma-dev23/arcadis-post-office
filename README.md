# Post Office Shipments

A small app for a post office to manage **post offices** and **shipments** (letters and packages). You can add, edit and remove both, move a shipment through its delivery statuses, and list shipments with paging and filters for shipment number, status, current location, weight category and type.

- **Backend:** ASP.NET Core 10 Web API, EF Core 10, PostgreSQL
- **Frontend:** React 19 + TypeScript (Vite)
- **Tests:** xUnit
- **Run:** Docker Compose

---

## How to run

### With Docker (recommended)

You only need [Docker Desktop](https://www.docker.com/products/docker-desktop/). From the repository root:

```bash
docker compose up --build
```

| What | URL |
|---|---|
| Web app | http://localhost:3000 |
| API docs (Swagger UI) | http://localhost:8080/swagger |
| PostgreSQL | `localhost:5432`, database / user / password: `postal` |

On first start the API creates the database schema (EF Core migrations) and seeds demo data: 4 post offices and 25 shipments with mixed types, weights and statuses.

To stop: `docker compose down`. To also delete the data and start fresh: `docker compose down -v`.

### Without Docker (for development)

Requires the .NET 10 SDK, Node.js 22+, and a PostgreSQL instance. The easiest way to get one is `docker compose up -d db`.

```bash
# API on http://localhost:5167 (Swagger at /swagger)
cd backend
dotnet run --project src/Postal.Api

# Web app on http://localhost:5173 (in a second terminal)
cd frontend
npm install
npm run dev
```

The connection string for local development is in `backend/src/Postal.Api/appsettings.Development.json`.

## Assumptions

The brief leaves some points open. These are the interpretations I chose:

1. **Listing and filters cover all shipments** (letters and packages), with an extra `type` filter to narrow it down.
2. **The actual weight is stored in kg** and the weight category is derived from it: under 1 kg, 1–5 kg (inclusive), over 5 kg. A stored category could drift out of sync with the weight; a derived one can't.
3. **Each shipment has an origin and a destination post office**, and they must be different.
4. **Status only moves forward:** *Received at origin* → *Received at destination* → *Delivered*. A new shipment starts at origin. Delivered shipments can't be advanced further (409).
5. **Current location is derived from the status:** the origin post office while at origin, the destination after that. The *location* filter uses the current location.
6. **The shipment number is generated by the system** (e.g. `SHP-7F3K9Q2A`), is unique, and is read-only. Search is case-insensitive and matches part of the number. Ambiguous characters (0/O, 1/I) are left out.
7. **A post office can't be deleted while shipments reference it** (409 Conflict). This protects the history of shipments.
8. **A post office is identified by a unique 5-digit ZIP code** and has a name. The "parcel centres" in the statuses are treated as the origin and destination post offices.
9. **No authentication**, as it was out of scope for this exercise (see *What I'd do next*).

## Design and key decisions

### Backend

```
backend/src/Postal.Api
  Domain/        Entities with their business rules (PostOffice, Shipment)
  Data/          AppDbContext, entity configurations, migrations, seed data
  Contracts/     Request/response DTOs
  Services/      Use cases: queries, rules that need the database, mapping to DTOs
  Controllers/   HTTP only: bind the request, call the service, return a result
backend/tests/Postal.Api.Tests
```

- **Business rules live in the domain entities.** `Shipment.AdvanceStatus()`, the weight category and the "origin ≠ destination" check are plain C#, so they're unit-tested without a database.
- **One API project with clear folders** instead of separate Domain / Application / Infrastructure projects. For an app this size the extra projects add ceremony without benefit. In a larger system I would split them.
- **No repository layer.** EF Core's `DbContext` already provides the unit of work and repositories, so services use it directly.
- **Services return DTOs, never EF entities.** Read queries use `AsNoTracking()` and project straight to DTOs with `Select`, so only the needed columns are loaded.
- **Filters run in the database.** "Current location" and "weight category" are derived values, so the service translates them into SQL conditions instead of filtering in memory. Paging sorts by `CreatedAt`, then `Id`, so the order is stable and rows never repeat between pages.
- **Errors are consistent `ProblemDetails`:**
  - **400:** validation failures (data annotations, plus C# `required` properties so missing fields aren't silently defaulted)
  - **404:** not found
  - **409:** a broken business rule (`DomainException`, handled in one place by `ExceptionHandler`)
- **The database protects itself too:** unique indexes on ZIP code and shipment number, check constraints for weight > 0 and origin ≠ destination, and `Restrict` delete on foreign keys.
- **Enums are sent as strings** in JSON (`"Delivered"` rather than `2`) and stored as strings in the database, which makes both readable.

### Frontend

```
frontend/src
  api/          client.ts (fetch wrapper) and types.ts (mirrors the API DTOs)
  pages/        ShipmentsPage, ShipmentFormPage, PostOfficesPage
  components/   ShipmentFilters, Pagination, StatusBadge
```

- **Plain `fetch` in one typed client**, no extra data libraries. Every call goes through `client.ts`, which also turns ProblemDetails errors into readable messages.
- **Shipment filters and the page number live in the URL** (e.g. `?status=Delivered&page=2`). They survive going to the edit form and back, can be bookmarked, and work with the browser's back button.
- **Out-of-date responses are ignored.** When typing in the search box, a slower earlier response can't overwrite a newer one.
- Loading and error states on every page. API errors, such as deleting a post office that's in use, are shown to the user.

### Docker

`docker-compose.yml` runs three containers:

- **db:** Postgres 17, with a volume so data survives restarts and a health check so the API waits until Postgres is ready.
- **api:** a multi-stage build that compiles with the .NET SDK image and runs on the smaller ASP.NET runtime image.
- **web:** Vite builds the static files, which nginx serves. Unknown paths fall back to `index.html` so deep links like `/shipments/3/edit` work.

## API overview

Base path `/api`. Full, interactive documentation is in Swagger UI at `/swagger`.

| Method | Route | Notes |
|---|---|---|
| GET | `/post-offices` | All post offices |
| GET | `/post-offices/{id}` | |
| POST | `/post-offices` | 409 if the ZIP code exists |
| PUT | `/post-offices/{id}` | |
| DELETE | `/post-offices/{id}` | 409 if shipments use it |
| GET | `/shipments` | Paging and filters, see below |
| GET | `/shipments/{id}` | |
| POST | `/shipments` | Generates the number; starts at *Received at origin* |
| PUT | `/shipments/{id}` | Edit type, weight, origin, destination |
| POST | `/shipments/{id}/advance-status` | Next status; 409 if already delivered |
| DELETE | `/shipments/{id}` | |

**List query parameters (all optional):** `page` (default 1), `pageSize` (default 10, max 100), `shipmentNumber`, `status`, `postOfficeId` (current location), `weightCategory`, `type`.

```json
{ "items": [ ... ], "page": 1, "pageSize": 10, "totalCount": 25 }
```

## Testing

```bash
cd backend
dotnet test
```

19 tests, focused on the logic rather than volume:

- **Domain:** weight category boundaries (0.999 / 1 / 5 / 5.01 kg), forward-only status changes, a delivered shipment can't advance, weight must be positive, origin ≠ destination.
- **Service** (EF Core InMemory provider):
  - create generates unique numbers and starts at origin; unknown post offices are rejected
  - each filter (status, weight category, current location, case-insensitive number search)
  - paging returns the right page and total count
  - a post office in use can't be deleted

The frontend was tested manually in the browser (every page and action).

## What I'd do next

- **Authentication and authorisation** with Microsoft Entra ID, e.g. counter staff vs. admins.
- **Status history:** record who changed a shipment's status and when, instead of keeping only the current status.
- **Optimistic concurrency** (a row version), so two people editing the same shipment don't overwrite each other.
- **Integration tests** against a real PostgreSQL using Testcontainers and `WebApplicationFactory`. The InMemory provider doesn't behave exactly like Postgres.
- **CI pipeline** (build, test, lint, Docker images) and **deployment** to Azure (App Service or Container Apps, Azure Database for PostgreSQL), running migrations in the pipeline rather than at startup.
- **Business rules to confirm with the business,** for example whether a delivered shipment may still be edited, or maximum weights for letters.
